# 計画のレビュー

**実装がまだ無い状態（`plan.md` しか無い）で見る観点。**
コードの観点（`checklist.md`）は当たらない。Null も Transaction も N+1 も、
まだ書かれていないものには問えない。

**運用（どこで共有するか・何を記録するか・承認の扱い）は `dev-flow` の
`plan-review.md` が持つ。ここには書かない。**

---

## `[issue]` の線

コードなら「バグ・要件違反」。**計画なら「このまま実装すると手戻りが確定する」。**

- 採用した案が、挙がっている制約を満たしていない
- 対象の集合が漏れていて、作り直しになる
- 完了条件が測れず、終わったかどうかを誰も言えない

**「別の案もありうる」は `[issue]` にしない。** それは `[suggestion]`。
判断を含む計画では意見の相違が尽きないので、**再現手順を示せないものは止めない。**

## 観点

### 1. 比較した案と採用理由

- **案が1つだけなら、比較していない。** なぜ他を採らなかったかが書かれているか
- 採用理由が「こちらのほうが良い」で終わっていないか。**何を基準に良いのか**
- **取り消した判断**が残っているか。前に採った案を捨てたなら、その理由

### 2. 対象の集合の出どころ

**「この集合はどこから来たか」に答えられるか。** 道具の列挙・API の結果・規約の一覧で
答えられないものは、**手で並べている**。

- 接頭辞・grep の範囲・時点・値の括り方・環境 — **漏れはここから出る**
- 件数が書いてあるなら、**どのコマンドで数えたか**

### 3. 完了条件

- **測れる形か。** 「正しく動く」ではなく、何がどうなったら終わりか
- 誰が確かめるか。**実機での確認が要るなら、その段があるか**

### 4. やらないこと

- 書かれているか。**無いと、レビューで際限なく広がる**
- やらない理由が書かれているか（「別チケット」なら、その番号）

### 5. 取り消す判断

- **壊れたときに戻せるか。** 戻し方が書かれているか
- 書き込みを伴うなら、**書き込む範囲が列挙されているか**（経路を辿って数えたか）

### 6. 重さの釣り合い

- リスク区分（`dev-flow` の `risk-policy.md`）と、計画の厚さが釣り合っているか
- **軽微なのに重い計画**は、書く側の時間を奪う
- **高リスクなのに薄い計画**は、実装中に判断が発生する

## テスト

**実行するものが無い。** 「未実行」と書いて閉じる。
**何も書かないと「全部通った」に見える。**

計画に検証の段が含まれているなら、**その手順が実行可能か**を見る
（存在しないコマンド・届かない環境を指していないか）。

## リポジトリ固有が優先

計画のテンプレートを持つリポジトリがある。**あるならそれが観点の正本。**
`dev-flow` を使っているなら `plan-template.md` の項目が揃っているかを見る。
ここの観点は汎用の既定にすぎない。
