# 出す指摘を選んでもらう

**本文を書く前に、候補を一覧で出す。** 書いてから削ると、捨てる文章を書くことになる。

## 出力の頭に「この PR」の3行

**候補一覧の項目ではない。** 候補一覧を出す回も出さない回も、**出力はここから始める**。
選ぶための材料ではなく、**読む人が、知らない分野の PR で何が起きているかを掴むため**のもの。

> 2026-10-28、候補一覧の項目1 として置いたところ、一覧を飛ばす回
> （指摘が少ない回）に**要約ごと消えた**。「一覧を出さない回も書く」と
> 但し書きを足しても消えたため、**一覧の外へ出した**。

## 候補一覧に出すのはこの5つだけ

**他は出さない。** 根拠・再現・詳細は**番号で聞かれてから**。

| | 中身 | 長さ |
|---|---|---|
| 1 | **何人で見たかと、その理由** | 1行。2人以上なら差も |
| 2 | **候補** | 1件1行 |
| 3 | **裏どり済み・問題なし** | 見出しだけを1行に並べる |
| 4 | **テスト** | コマンドと結果だけ。**未実行も書く** |
| 5 | **副作用の報告**（あれば） | 1〜2行 |

**1 は単独のときも書く。** 黙って1人で決めない（`cross-review.md`）。

## 要約は「出どころ」を必ず書く

**要約を書くのも、レビューするのと同じエージェント。** 読み違えたら、
**自信のある誤った要約**が出る。**読む人は不慣れな分野でそれを読む**ので、
間違いに気づけない。**誤った要約は、無いより悪い。**

```
この PR（本文とチケットから）:     ← 書いてあることを写した
この PR（差分を読んだ私の読み）:   ← 本文に説明が無く、自分で立てた
この PR（本文から。ただし影響範囲は私の読み）:
```

**3行目（影響範囲）は、不慣れな分野でいちばん効く。** どこを重点的に見ればいいかが決まる。
**本文に書かれていないことが多い**ので、出どころの区別がとくに要る。

**表組み・コードブロック・再現手順を候補一覧の段に置かない。**
選ぶのに要らないものが混じると、**選ぶ前に読む量が増える**。

**例外は1つ。判定が割れたときだけ、その根拠を1行添える。**
選ぶ側は「自分の `[issue]` を信じるか」を決める必要があり、
**再現できたかどうかがその判断材料**になる。

```
判定が割れた根拠: #1 は変異（2つ目のブロックに架空の値）で本番・自己テストとも
  緑のまま通ることを再現済み。相手は [issue] 0 件
```

> 3 回続けて余計なものが出た（裏どりの詳細 → テスト結果の表 → 再現の表）。
> ケースを足しても次が出るので、**出してよいものを固定した。**

## 一覧の形

**この形をそのまま使う。** 表組みにしない。番号は算用数字。

```
この PR（本文とチケットから）:
  月末に請求書を1件ずつ出していて時間がかかっていた
  一覧に「一括出力」を足し、選んだ分をまとめて PDF にする
  影響: 管理画面の請求一覧だけ。既存の単票出力は変えない

レビュー: 単独（計画のリスク区分が「軽微」）

候補 9 件。出すものを選んでください（番号で。「全部」「issue だけ」も可）。
あわせて出力先も: ① 貼れる markdown（投稿しない） / ② GitHub へ投稿

 1. [issue]       `Foo.php:42`  $estimate が null のとき落ちる
 2. [suggestion]  `Foo.php:60`  この4行はヘルパーに寄せられる
 3. [suggestion]  `Bar.ts:88`   取得失敗と 0 を区別できない
 4. [nit]         `Baz.php:12`  命名が既存と揃っていない
 5. [ask]         `Qux.php:30`  この分岐は意図的ですか
 ...

裏どり済み・問題なし 7 件: 金額の整合 / ロックの経路 / メタデータ列 /
  一意制約 / ガードの手口 / ランナー制約 / テストの有無（詳細は番号で）

クロスレビュー: 両方 3 / 片方だけ 5 / 格付けが割れた 1（#7）
```

**1件1行。** 根拠は書かない（選ぶのに要らない）。
**質問は1回にまとめる。** 出すものと出力先を別々に聞かない。

### 推奨を添える

**選ぶ基準が `local/<スキル名>.md` にあれば、それに沿った推奨を1行足す。**

```
推奨: 1〜4（issue + suggestion が 5 件未満なので nit から #6 を足した）
```

**ただし候補は全部出す。** 推奨だけ出して候補を伏せると、
**見落としの可能性があるものが見えなくなる**（片方だけの指摘を残す意味が消える）。
基準が無ければ**推奨を添えない。** 勝手に決めない。

- **`[issue]` は既定で出す。** 外すなら理由を聞く（マージを止める判断を落とすことになる）
- **格付けが割れたものには印を付ける。** 選ぶ側が判断材料にできる
- 順番は `[issue]` → `[suggestion]` → `[nit]` → `[ask]`

## 裏どりして問題なしだったものも出す

**指摘にならなかったものこそ、選ぶ人の判断材料になる。**
何を見て、何を見ていないかが分かる。**見ていない範囲を黙らせない。**

**ただし畳む。** 候補一覧より長くなると、選ぶ作業が重くなる。

- **見出しだけを1行に並べる。** 根拠は書かない
- 詳細が要るものは**番号で聞かれてから出す**
- 投稿する本文へ入れるかは、選ぶ人が決める（既定は入れない）

## テスト

```
テスト: check-color-sync 緑 / 自己テスト 44・149・36・85 すべて緑 /
  アセットビルド 未実行（node_modules 無し）
```

**未実行のものは必ず書く。** 落とすと「全部通った」に見える。
詳細（どのコマンドをどう流したか）は、**選ばれた本文に書く**。

## 選ばれなかったものの扱い

**消す。** 本文にも畳んだ場所にも残さない。「選ばれなかった」という情報自体がノイズ。

**ただし件数は総評に出す。**

```
- [issue] 1 / [suggestion] 2 / [nit] 0 / [ask] 1（候補 9 件から選択）
```

**何件から選んだかが分かれば、落とした量は伝わる。** 中身は伝えない。

## いつ選んでもらわないか

**指摘が 3 件以下のとき。** 選ぶ手間のほうが大きい。そのまま本文を書く。

**ただし出力の頭の3行（この PR）は書く。** 一覧の外にあるので、一覧を飛ばしても残る。

**選ぶ人がいないとき**（自動実行など）は、`[issue]` のみ出す。
**勝手に全部出さない。**
