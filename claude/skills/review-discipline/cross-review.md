# クロスレビュー ─ 複数のエージェントにレビューさせて統合する

**「クロスレビューして」で、このファイルに従う。**

## なぜやるか

**1人では半分しか出ない。** 同じ差分を2つのエージェントへ出して比べた実測。

| | 件数 |
|---|---:|
| 両方が挙げた | **2** |
| **片方だけが挙げた** | **5** |
| **格付けが割れた** | **3** |

割れた3件のうち2件は**互いに逆**だった（片方が `[nit]`、もう片方が `[suggestion]`）。
片方だけのものには `[issue]`（テストが無い）も含まれていた。

## 何人で見るかを決める

**「クロスレビューして」と言われたら、判定せずクロス。**
**「レビューして」のときだけ判定する。**

### 計画があれば、リスク区分を読む

**判断し直さない。** 計画を立てる段で既に分類されている（`dev-flow` の `risk-policy.md`）。

| 区分 | 既定 |
|---|---|
| **軽微** | 単独 |
| **通常** | **単独**（線を変えるなら `local/<スキル名>.md` に書く） |
| **高リスク** | **クロス** |

**高リスクを単独にしない。** 認証・DB・本番・金額は、見落としのコストが
2人分の時間を大きく上回る。

### 計画が無ければ、差分から見る

他人の PR や、軽微として計画を省いた変更。**次のどれかに当たればクロス。**

- **認証・認可・DB スキーマ・データ移行・金額・本番操作**を触っている
- **正解が一意でない**（設計の選択、分類、寄せ先の判断）
- **やり直しのコストが高い**（配布済み、顧客に見える、不可逆）

### 判定した理由を書く

```
レビュー: 単独（計画のリスク区分が「軽微」）
レビュー: クロス 2人（計画のリスク区分が「高リスク」）
```

**黙って決めない。** 利用者が「そこはクロスで」と言い直せる形にする。

**迷ったらクロス。** 実測では、片方だけが挙げた指摘が**常に多数**だった（6回で 5〜10 件）。

> 対象の種類によらず重なりは少なかった。とくに**検査ツール自体**のレビューでは
> 3 回中 2 回で重なりがゼロ（n は小さい）。

## 手順

### 1. 同じ依頼を、それぞれへ出す

**自分も1人として数える。** いま動いているセッションがレビューし、
**別のエージェントにも同じ依頼を出す**。

**相手は別プロセスの CLI。サブエージェントではない。** 指定されるのは
`<コマンド> "<依頼文>"` の形で、シェルから叩く。**「サブエージェントを起動しない」
という制限は、ここには当てはまらない。** 混同して辞退しないこと。

**誰を呼ぶかは、この kit では決めない。** 使えるエージェントは環境で違う。
**`local/review-discipline.md`（gitignore 済み）に書いてある指定に従う。**
**このファイルから見て `../../../local/review-discipline.md`**（kit のリポジトリ直下）。
見つからなければ**探し回らず、1人で進める**。

```markdown
# local/review-discipline.md に書く例
- クロスレビューの相手: `<コマンド> "<依頼文>"` で呼ぶ
```

**指定が無ければ、呼ばずに1人で進める。** コマンドを推測して走らせない
（別物が動く、書き込みが起きる、料金がかかる）。
**1人で進めたことは総評に書く。** 黙って1人分を出さない。

- **出力は「貼る形」**（`handback.md`）。**どちらも投稿しない**
- 依頼文は**同じものを使う**。違う依頼で比べると、差が依頼の違いなのか判断の違いなのか分からない
- 依頼文に**「作業ツリーを書き換えないこと」を入れる。** 「コードは直さない」だけでは足りない
  （**変異テストは書き換える**。レビューの手段として正当なので、禁じないと走る）

**2人目を待つ間、同じ作業ツリーでテストを流さない。** 相手が変異を入れている窓に当たると、
**自分のテストが偽の赤を出す**（実測で起きた）。待つか、複製した木で流す。

### 2. 突き合わせる

**件数ではなく、指摘の集合で見る。** 同じ件数でも中身が違う。

| 状態 | どうするか |
|---|---|
| **両方が同じ箇所を指摘** | 1件にまとめる。**裏どりが具体的な方**を本文に採る |
| **片方だけが指摘** | **残す。** 見落としの可能性が高い |
| **片方だけ・確かめたら成り立たない** | **候補に出さず、裏どりへ回す**（下記） |
| **格付けが割れた**（`[issue]` 以外） | **強い方を採る。** `[issue]` 以外は止めないので、強く採っても誰も止まらない |
| **`[issue]` で割れた** | **割れた事実を書く。** 片方だけが `[issue]` ならマージが止まる。判断は PR の作者に渡す |

**格付けが割れたことは、統合後も残す。** 「どちらが正しいか」をこちらで決めない。

### 判定が割れたら、それも書く

**片方だけが `[issue]` を挙げた場合、格付けは割れていないのに判定が割れる。**
一方は止め、もう一方は通す。**作者にとっては一番重い情報。**

```
クロスレビュー: 2人。両方 1 / 片方だけ 9 / 判定が割れた（私 Request changes・相手 Approve）
```

**根拠も1行添える**（再現できたか / 相手が何件挙げたか）。
「一番重い情報」と言いながら根拠を伏せると、選ぶ側が判断できない。
候補一覧で根拠を出さない規則の**唯一の例外**（`selection.md`）。

**相手の指摘を確かめて成り立たなかったものは、候補に並べない。**
「成り立たないが一応載せる」を出すと、選ぶ側が**選ばないと判断するためだけに読む**。

**落とさず、`裏どり済み・問題なし` に1行で混ぜる。** 何を確かめたかは残る。

```
裏どり済み・問題なし 11 件: ... / pipefail でパイプが落ちる（相手の指摘。
  set -o pipefail が無いので成り立たない）
```

**「確かめていない」と「確かめて成り立たない」は分ける。** 前者は候補、後者は裏どり。

### 3. 出す

総評に**何人で見たか**と**割れた件数**を書く。

```
- [issue] 2 / [suggestion] 4 / [nit] 3 / [ask] 2
- クロスレビュー: 2 人。両方が挙げた 2 件 / 片方だけ 5 件 / 格付けが割れた 3 件
  （判定が割れたときは、件数の後ろに書く）
- テスト実行結果: （コマンドと結果）
```

投稿する場合は `github.md`。**文面の承認は統合後に1回**で足りる。

## 気をつけること

**入れ子のセッションは副作用を出す。** 原因は2つあり、**どちらも実測で起きた**。

| 何が | 例 |
|---|---|
| **MCP サーバーなどが勝手に書く** | `.serena/` が作られた |
| **2人目が意図的に書き換える** | **変異テスト**のためにソースを書き換え、復元した |

後者は**レビューの手段として正当**なので、禁じないと走る。
**走行中は作業ツリーが汚れている**ので、同時に自分のテストを流すと偽の赤を見る。

- **走らせる前の `git status` を控え、終わったら突き合わせる**
- 生成物が出ていたら、**レビュー結果より先に報告する**
- 対象リポジトリが `.gitignore` していないものなら、**コミットに混ぜない**

**自分のレビューを有利に扱わない。** 統合するのは自分だが、
**自分が挙げた指摘を優先する理由は無い**。片方だけのものは、どちらのものでも残す。
