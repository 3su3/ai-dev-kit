# レビューの規律

## 立場

- **コードを書き換えない。** 修正を頼まれていない限り、レビューに徹する
- 好みで指摘しない。**指摘には必ず根拠を添える**
- 要件を満たしている実装を、設計思想だけで否定しない
- 今回のスコープ外の改善は `[nit]` に落とす
- レビューは**実装とは別のセッション**で行う。経緯を知っていると流してしまう

## 観点

**コード**: 要件 / 安全性 / データ整合性 / 保守性 / 既存との整合性 / テスト / ログ /
パフォーマンス / 変更規模（`checklist.md`）

**計画だけのとき**: 比較した案と採用理由 / 対象の集合の出どころ / 完了条件 /
やらないこと / 取り消す判断（`plan-checklist.md`）。
`[issue]` は「**このまま実装すると手戻りが確定する**」。テストは「未実行」で閉じる

**リポジトリ固有の観点を先に確認する**（`ls REVIEW.md docs/development/`）。
「**指摘しなくてよい項目**」まで定めていることがあり、**食い違ったらそちらに従う**。

## テスト

**変更の影響範囲に対応するテストを特定して実行する。** 失敗したら `[issue]`。
テストが無い変更（CSS・ドキュメント等）はビルドの成功を確認する。

# 出力

| 出力先 | 形 | 読むもの |
|---|---|---|
| GitHub の PR | 総評は本文、指摘はインラインコメント | `github.md` |
| 実装セッションへ返す（セルフレビュー） | 貼れる markdown。**投稿しないので文面承認は不要** | `handback.md` |
| 複数で見る（クロスレビュー） | **別のエージェントへも同じ依頼を出す** | `cross-review.md` |


## 接頭辞

指摘の頭に接頭辞を付ける。**それ以外の見出し（Critical / Warning / Suggestion）は使わない。**

| 接頭辞 | 意味 | マージを止めるか |
|---|---|---|
| `[issue]` | バグ / 要件違反 / データ不整合 / セキュリティ / テスト不足 | **止める** |
| `[suggestion]` | 保守性・可読性・設計上の懸念・性能懸念。直したほうがよい | 止めない |
| `[nit]` | 好みに近い、任意。スコープ外の改善もここ | 止めない |
| `[ask]` | 判断がつかないので聞きたい。断定しない | 止めない |

**褒めない。** 作者が何かする必要のないものは、レビューの出力に載せない。

## 本文（総評）の形

**冒頭の2行で「何をすればいいか」を言う。** 経緯・前置き・調査の手順から始めない。

```
（1行目: 作者が何をすればいいか。「直すのは〜だけ」「このまま進んでよい」）
（2〜4行: なぜそう判断したか。根拠の詳細はインラインへ送る）

- [issue] 2 / [suggestion] 3 / [nit] 1
- 差分に現れない行への指摘: （あればここに書く。無ければこの行を消す）
- テスト実行結果: （コマンドと結果）
```

1文に根拠・条件・反証を詰めない。詳細は `readability.md`。

**インラインコメントは差分に現れる行にしか付けられない。**
差分外のファイル・既存コードへの指摘は、本文に「どのファイルの何行目か」を明記して書く。
インラインに付けられなかったことを黙って落とさない。

## 判定

**ブロッカーが無ければ承認する。**

| 判定 | 使うとき |
|---|---|
| Request changes | `[issue]` が1件以上ある |
| Comment | `[issue]` は無いが、**答えが来ないと判断できない `[ask]`** がある |
| Approve | それ以外。**読みが立っている確認の `[ask]`** は何件あっても承認する |

迷ったら `judgement.md`。

## 出し方

1. **候補を一覧で出し、選んでもらう**（本文を書く前。返す場合も行う）
2. **投稿する前に文面の承認を得る。** 取り消しが効かない

**出力は「この PR」の3行から始める**（目的 / 打ち手 / 影響範囲。**出どころを書く**）。
**候補一覧を出さない回も書く。** これは選ぶための材料ではない。

### 候補一覧に出すのはこの5つだけ

**他は出さない。** 根拠・再現・詳細は**番号で聞かれてから**。

1. **何人で見たかと、その理由** — 1行。2人以上なら差も
2. **候補** — **1件1行。根拠は書かない**
3. **裏どり済み・問題なし** — 見出しだけを1行に並べる
4. **テスト** — コマンドと結果だけ。**未実行も書く**
5. **副作用の報告**（あれば） — 1〜2行

```
この PR（本文から）:
  月末に請求書を1件ずつ出していた
  一覧に「一括出力」を足し、選んだ分をまとめて PDF にする
  影響: 管理画面の請求一覧だけ

レビュー: 単独（計画のリスク区分が「軽微」）

候補 9 件。出すものと出力先を選んでください
（番号で。出力先は ① 貼れる / ② GitHub）

 1. [issue]  `Foo.php:42`  $estimate が null のとき落ちる
 2. [nit]    `Baz.php:12`  命名が既存と揃っていない

裏どり済み・問題なし 7 件: 金額の整合 / ロックの経路（詳細は番号で）
```

**指摘が3件以下なら選んでもらわない。** そのまま本文を書く。
詳しくは `selection.md`。

## 同じ指摘が3回続いたら

**どちらにするかは依頼者に選んでもらう。** 判断そのものは①層の原則（解き方を変えるか主張を狭めるか）。
