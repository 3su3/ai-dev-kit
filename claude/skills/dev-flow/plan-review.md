# Plan レビューの共有と引き継ぎ

この手順は実装前の Plan レビューの**運用**（共有先・記録・承認の扱い）を扱う。**何を見るかの観点は持たない。** 計画の観点は `review-discipline` の `plan-checklist.md`、実装後のコードレビューは `review-discipline`、その PR の指摘対応は `review-response` が扱う。対象リポジトリの規則、アクセス権、機密情報の扱いを優先する。

## レビュー経路を選ぶ

- Human 自身が Plan をレビューする場合は、対象リポジトリが認めるローカルの経路を使える。AI レビュー用の共有先や PR を追加で要求しない。リスクに応じた Plan と Human の実装承認は引き続き必要。
- AI に Plan レビューを依頼する場合は、双方が読め、必要な担当者が書ける永続的な共有先を選ぶ。既存の Issue、PR、設計文書などを使い、同じ説明の複製や不要な Issue を増やさない。GitHub を利用できる場合、Draft PR は推奨候補であり必須ではない。
- Plan レビュー用の Draft PR がある場合は、原則として同じ PR で実装と実装レビューを続ける。対象リポジトリの規則や Human の指示が優先される。別の PR が必要な場合は、作成前に理由と PR の関係を明示する。Draft PR を作ること自体は必須ではない。
- 公開範囲、アクセス権、Plan の内容を共有できるかを事前に確認する。安全な共有先がない場合、アクセスできない場合、機密や権利に疑義がある場合、対象リポジトリの規則と衝突する場合は共有を止め、Human に確認する。確認待ちの内容を別媒体へ転記しない。

## 共有記録に残すこと

AI レビューを選んだときは、既存の媒体を利用して次を追えるようにする。媒体の URL、ファイルパス、コメント ID などはその媒体が提供するものを使う。チャット固有の記憶や Plan のチェック欄だけで状態を判断しない。

1. Plan の所在、レビュー対象の commit SHA など変更されない版識別子、レビュー依頼先。
2. 指摘ごとの対象版、理由、対応方針、修正先または見送る理由、未解決・未確認の状態。
3. レビュー AI が確認した版と、各指摘の解消判断。Plan を修正したら新版を示し、変更差分を再レビューする。旧版への LGTM を新版へ流用しない。
4. Human が未確認・未解決事項をどう扱うか判断した記録と、対象版を明示した実装承認の記録。二つは別の判断として追えるようにする。

## 指摘への対応と完了

1. 実装 AI は指摘の対象箇所と前提を確認し、修正・見送り・保留の理由を共有記録に残す。実装 AI の対応済み申告だけでは完了しない。
2. レビュー AI が該当版と対応を再確認し、指摘ごとの解消判断を共有記録に残す。Plan の変更後は旧版のレビュー結果を新版へ引き継がない。
3. レビュー AI が利用できない、または再確認できない場合は未確認として残す。未解決の指摘がある場合も隠さず、Human に対応方針の明示判断を求める。Human の判断は AI レビュー完了と別に記録する。Human が続行を認めても、未確認を AI の LGTM に書き換えない。
4. 次の担当 AI は共有記録を再読し、対象版、指摘状態、Human の判断と実装承認の根拠を確認する。読み出せない、版が一致しない、必要な判断がない場合は実装を始めず Human に確認する。

AI の LGTM は Human の実装承認ではない。実装開始には、対象リポジトリが要求する承認と、現在の Plan 版に対する Human の明示的な実装承認が必要。承認後に Plan を実質変更した場合は、新版のレビューと承認を再確認する。Plan の共有・レビューは Ready 化、merge、設定同期、公開の権限を与えない。
