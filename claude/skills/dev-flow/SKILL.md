# 開発フロー

役割を分けて進める。**Role（誰として振る舞うか）と Strategy（どの方針で実装するか）は独立**で、
方針を増やしても役割は増やさない。

## どこから入るか

**書き始める前に、既にある計画を探す。** 別のセッション・別のエージェントが作っていることがある。
**見つけたら書き直さない。**

| 見つかったもの | 入口 |
|---|---|
| 承認された計画がある | **4. 実装**（`implementer.md`）。計画を書き直さない |
| 計画はあるが承認が確認できない | **3. 承認確認**（`plan-review.md`）。承認が無ければ手を止める |
| 計画が無い | **1. 調査**から |

探す場所は対象リポジトリの規約で決まる。**規約が計画の置き場を定めているなら、そこを先に見る。**
加えて、次の2つは置き場が未定義でも効く。

```bash
git diff --name-only $(git merge-base HEAD main)..HEAD   # このブランチで既に足された文書
gh pr view --json body,files                             # PR に計画が乗っていることがある
```

**「計画が見つからない」と決める前に、少なくともこの2つは実行する。**
渡されたのが PR や Issue の URL だけでも、計画はその中にあることが多い。

## 順番

1. **調査** — `leader.md` の調査チェックリストに沿う。調査不足のまま計画を書かない
2. **リスク分類と計画** — `risk-policy.md` に従って変更を分類する。通常・高リスクは `plan-template.md` の項目に沿って、対象リポジトリが指定する保存先・命名で残す。軽微な変更はリポジトリの規則が許す場合のみ、Issue等の永続的な短い記録で代替できる
   Acceptance の検証責任も `risk-policy.md` の手順で整理する。
3. **Plan レビューと承認確認** — `plan-review.md` に従い、Human レビューまたは AI レビューを経て、対象リポジトリが要求する Human の実装承認を確認する。必要な承認がない場合は**手を止める**。AI の LGTM やリスク分類だけで承認を省略しない
4. **実装** — `implementer.md` に従う。重要な振る舞いには**TDD（Red → Green → Refactor）**を適用する
5. **レビュー** — `review-discipline` スキルに従い、**別セッションで**行う
6. **実機での確認**（その段がある場合） — 検証環境へ反映して確かめる工程。
   **いつ行うかは対象リポジトリの規約と計画が決める。** ここでは順番を決めない。
   報告は `verification-report.md`。**結論（問題なし / 懸念あり）を1語目に置く**

## どれを読むか

| 場面 | 読むもの |
|---|---|
| 調査・計画を立てる | `risk-policy.md` / `leader.md` / `plan-template.md` |
| Plan をレビュー・修正・引き継ぐ | `plan-review.md` |
| 承認された計画を実装する | `implementer.md` |
| 方針を選ぶ | `strategies.md` |
| 複数案を比べる | `compare-template.md` |
| 実機で確かめたあと報告する | `verification-report.md` |
| 流れ全体を確認する | `workflow.md` |

## 実装方針を名指しで選ぶ

実装に入る前に1行で宣言する。黙って選ばない。詳細は `strategies.md`。

| 方針 | 最優先するもの |
|---|---|
| Minimal | 影響を受ける機能・画面の数。差分行数ではない |
| Pattern | 既存の同種実装との一貫性 |
| Robust | 異常系・境界値・責務分離 |

## 役割を分けるセッションの切り方

- Leader → Implementer（単独実装）: 同一セッションで可。計画ファイルが仲介する
- Leader → Implementer（並列実装）: **別セッション**。互いの案を参照させない
- Reviewer: **常に別セッション**。実装経緯を知っていると「まあ大丈夫だろう」で流れる

## 手を止める線

- 対象リポジトリが要求する計画・承認が満たされていない → 実装しない
- 承認された範囲の外に直したい箇所が見つかった → **直さずに報告**し、別件として起票する
- コンフリクトが出た → 自動で解決しない
- **決まっている順番を、自分の判断で前後させない。** とくに
  **まだ来ていない工程を、利用者が選べる形で提案しない**（選択肢に出した時点で順番は崩れる）。
  どこまで終わったかと、次に何が要るかを報告して止まる。
  **順番が決まっていないなら、決めてもらう**（自分で決めて進めない）
- その他の停止条件は `implementer.md` の「作業を停止する条件」

## 完了の条件

適用可能なテスト・Lint・静的解析の結果を記録し、未実行を成功扱いせず、対象リポジトリが要求するレビュー・承認を満たす。

## 既定

- 適用可能なテスト・Lint・静的解析を実施する。未実行・利用不可は成功扱いせず理由と代替確認を記録する
- 静的解析のレベルなどの数値は、リポジトリの設定ファイルに従う。ここに書き写さない
- Plan・Journalの保存先・命名、ブランチ名、Issue・PR運用、テストコマンドはリポジトリ規約に従う。未定義なら既存運用を調査してHumanに確認し、勝手に規約を新設しない（`CLAUDE.md` / `AGENTS.md` から辿れる開発ガイドを先に見る）

コミット規約・PR の出し方のような**流儀で変わるもの**はここに書かない。
使う人の `local/preferences.md`（gitignore 済み）に置く。
