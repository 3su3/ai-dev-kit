# レビュー指摘への対応

## 立場

**指摘は仮説であって、事実ではない。** 人のレビューでも AI のレビューでも、
前提の読み違い・差分だけを見たことによる誤り・既に別の場所で担保されている件が混じる。

**全部取り込まない。** 取り込むかどうかは、**コードで裏どりしてから**決める。
「指摘されたから直す」は、動いているものを壊す経路になる。

逆に、**裏どりせずに反論もしない。** どちらも同じ怠慢。

## 裏どりの手順

指摘1件ごとに、次を実際にやってから判断する。読まずに判断しない。

1. 指摘が指す**コードを開いて読む**。差分だけでなく、その前後と呼び出し元
2. 主張が成り立つ**条件を具体化する**（どんな入力・状態で壊れるか）
3. 可能なら**再現させる**（テストを書く・実行する・ログを見る）
4. 既に別の場所で担保されていないか確認する（上位のバリデーション、型、DB 制約、既存テスト）

## 3つに振り分ける

| | 判定 | 扱い |
|---|---|---|
| **① 壊れている** | **再現手順が示せる**誤り | **直す** |
| **② 範囲外** | この変更では起きない／別の網で捕まる | **限界を書いて閉じる** |
| **③ 別案** | どちらでも成立する。方針や好みの違い | **決めた理由を記録して閉じる** |

**再現手順を示せないものは ① にしない。** 「〜し得る」だけでは ① にならない。
②③に振ったものは、同じ指摘が再び来ても「記載済み」で返す。これが打ち切りの線。

**リポジトリに指摘の扱いを定めた文書があれば、そちらが優先。** 先に確認する。

```bash
ls REVIEW.md CONTRIBUTING.md docs/ 2>/dev/null
```

## 返信

**スレッドごとに返信する。** まとめて本文に書かない。指摘した人が自分の指摘の行で読める。

書くのは3つだけ。

- **どう判断したか**（①②③のどれか）
- **何を見てそう判断したか**（読んだファイル・走らせたテスト・再現の有無）
- **何をしたか / しなかったか**

②③で閉じるときは、**相手が間違っていたとは書かない。** 範囲を明示して閉じる。

> 裏どりしました。`config` は呼び出し側が全キーを持つ前提の内部関数で、既定値での続行は想定どおりでした。
> ただし前提がコードに書かれていないので docstring に明記します。（②範囲外）

## resolve

**対応したスレッドだけ閉じる。** 判断が済んで返信したものが対象。

- **返信していないスレッドは閉じない**
- **まとめて閉じない。** 返信している間に新しい指摘が届いていることがある
- 相手が質問していて、まだ答えが届いていないスレッドは開けておく
- **指摘した本人が閉じるのが筋**のチームもある。リポジトリの慣習を確認する

> 自分の指摘でないものを「片付いて見えるから」閉じない。拾わなかった指摘を
> 黙って消す経路になる。

## 出し方

**投稿前に必ず文面の承認を得る。** 返信は人に届く発信で、**削除しても通知は取り消せない**。
下書きを提示して待つ。

**GitHub の場合は同梱の `github.md` を読む。** 返信と resolve の操作、
どちらが取り消せるかがある。

## 依頼者本人からの指摘

会話の相手（依頼者）が直接コメントで指摘してきた場合は、**PR に返信せず会話で返す。**
スレッドへの返信は、自分以外のレビュアーに届けるためのもの。

## 同じ指摘が3回続いたら

ケースを足すのをやめて、**判定の根拠そのものを差し替える**か、**範囲を明示して打ち切る**。
どちらにするかは依頼者に選んでもらう。
