# 実装計画: AI による Plan レビューの共有と引き継ぎ

> **状態: 完了** — PR [#6](https://github.com/3su3/ai-dev-kit/pull/6) でマージ済み。成果物は `claude/skills/dev-flow/plan-review.md`。

関連: [Issue #5](https://github.com/3su3/ai-dev-kit/issues/5)


# 1. 概要

## 背景

別の AI が Plan をレビューする際、Human が本文や結果をチャット間で転記する運用には、判断理由と未解決事項が失われる余地がある。

## 目的

AI レビューを選ぶ場合に共有記録から Plan、指摘、対応、未解決事項、Human の実装承認を復元できるようにする。Human 自身のローカル Plan レビューは続けられるようにする。

## 対応内容

既存 dev-flow に Plan 作成 → AI レビュー（任意）→ 修正 → Human 実装承認の段階と停止条件を加える。共有媒体は対象リポジトリの規則に従い、Draft PR は利用可能な候補として扱う。

# 2. ビジネス向けサマリー（必要な場合のみ）

## 変更内容

AI が共同で Plan を扱う際の記録先、引き継ぎ、承認境界を明確にする。

## Before / After

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| AI 間の Plan 受け渡し | 共通の手順がない | 双方が読める永続記録を選び、所在を示す |
| 指摘・対応 | 次の担当者への引き継ぎが未定義 | 指摘ごとの対応と未解決事項を記録から再読する |
| 実装開始 | 計画承認を要求 | AI の LGTM と Human の実装承認を明示的に区別する |

## 業務への影響

Human の手動転記を減らし、承認判断に必要な経緯を共有記録から確認できる。

## 影響しないこと

導入先の Issue・PR 運用、共有先の権限設定、Human によるローカルレビュー、merge 権限は変更しない。

# 3. 現状調査

## 現在の実装

`dev-flow/SKILL.md` と `workflow.md` は調査、Plan、承認、実装、別セッションの実装レビューを定める。`risk-policy.md` は対象リポジトリの規則・承認・機密の扱いを優先する。`leader.md`、`plan-template.md`、`implementer.md` は Plan 作成と再読を求めるが、Plan を別の AI がレビューする経路は定めていない。

## 関連する実装

- `review-discipline` は実装後のコードレビューと投稿前の文面承認を扱う。Plan レビューと混同しない。
- `review-response` は PR の指摘をコードで裏どりして返信・resolve する手順を扱う。Plan 指摘にはそのまま適用しない。
- `CONTRIBUTING.md` はこのリポジトリの Public-ready と変更理由の追跡を要求し、既存の Issue・PR・設計文書を利用できる。
- `docs/public-ready-decision-traceability-plan.md` が Plan の配置例。Plan の保存先を全導入先へ一律指定する規則はない。
- `tests/verify-dev-flow-risk.py` は dev-flow の静的整合性を検査する。実際のエージェント行動までは保証しない。
- 文書による手順変更であり、クラス・API・DB・CSS の継承・呼び出し関係は該当しない。参照関係は上記文書とテストを対象に調べた。

## 問題点

共有先の選択、Plan 指摘の記録・修正・再読、未解決事項の扱いが未定義。AI の LGTM が実装承認と誤読される可能性がある。

# 4. 実装方針

## 検討事項

Human のローカルレビューを保ちながら、AI レビュー時だけ共有記録を必須にする。媒体とアクセス権は対象リポジトリの規則に委ねる。承認の根拠はチャット記憶やチェック欄ではなく、追跡できる Human の明示判断とする。

## 方針候補

### 案A

#### 内容

AI レビューは常に GitHub Draft PR 上で行う。

#### メリット

差分と会話を一箇所に集めやすい。

#### デメリット

GitHub を使わない導入先や PR を許さない段階に適用できず、Issue の制約に反する。

### 案B

#### 内容

共有記録に必要な情報と手順を定義し、Draft PR・既存 Issue・設計文書などから対象リポジトリが許す媒体を選ぶ。

#### メリット

既存運用を使え、Human ローカルレビューも維持できる。

#### デメリット

媒体ごとのコメント・版管理方法は対象リポジトリに依存する。

## 採用予定の方針

**Pattern、案B。** 既存の規則優先、永続 Plan、Human 承認ゲートの形に沿って記述する。AI レビュー時には、Plan の所在とレビュー対象の commit SHA 等の不変な版識別子、指摘・判断理由・対応、未解決事項、Human 承認の所在を再構築できることを共通要件にする。同じ内容を別媒体へ重複記録しない。

Plan を修正したら新版の識別子を記録し、旧版への LGTM を新版のレビュー完了として流用しない。レビュー AI は変更差分と該当版を再確認し、各指摘の解消判断を共有記録へ残す。実装 AI の「対応済み」申告だけではレビュー完了とみなさない。レビュー AI が利用できない、または再確認できない場合は未確認として残し、Human に対応方針の明示判断を求める。この Human 判断は AI レビュー完了とは別に記録し、実装承認とも混同しない。

## 採用理由

Issue の制約を満たしつつ、導入先の手順と権限を変えずに共通の引き継ぎ条件を定義できる。

# 6. 影響範囲

## 影響を受ける機能

- dev-flow を使う AI の Plan 作成、AI レビュー、修正、実装開始判断。
- GitHub を使える環境での Draft PR PoC と、使わない場合の手順確認。

## 影響しない機能

- 実装後のコードレビュー規律、導入先の Issue・PR・merge・公開設定、ハーネスの同期コマンド。

## 想定されるリスク

- **高リスク**: 共通ハーネスの承認境界と複数 AI の行動に影響する。AI の LGTM から実装を開始する誤りを防ぐ必要がある。
- 旧版への LGTM や実装 AI の対応済み申告を、新版のレビュー完了と誤認する危険がある。未確認のまま進めるかは Human の明示判断を要し、その判断は AI レビュー完了や実装承認と分ける。
- 共有先の権限不足、機密疑義、導入先規則との衝突時は共有や実装を止め、Human に確認する。
- Draft PR で Plan を共有しても merge・公開・同期は自動的に許可されない。
- 復旧は文書・検査の差分を戻す。配布済みの環境は対象者の確認を経て再同期する。

# 7. テスト計画

## 追加するテスト

### 正常系

- Human ローカルレビュー経路が残ること、AI レビュー時に共有記録から Plan の対象版・指摘・対応・レビュー AI の再確認・Human 承認を再構築できることを静的検査と手順追跡で確認する。
- GitHub Draft PR を使える場合に、Plan とレビュー指摘を双方が読める PoC を行う。投稿・PR 作成は権限と対象リポジトリ規則を確認してから行う。

### 異常系

- 旧版への LGTM の流用、実装 AI の対応済み申告だけでの完了、レビュー AI の利用・再確認不可、未解決の指摘、共有先へのアクセス不可、機密疑義、導入先規則との衝突を想定し、未確認の記録・Human 判断・実装開始や共有の停止に至る文面か検査する。
- 静的検査に意図的な規則欠落を与え、赤になることを確かめる。

### 境界値

- GitHub を使わない共有経路、AI レビューを選ばない Human レビュー経路でも不要な PR・Issue を要求しないことを確認する。

## リグレッション確認

- `python3 tests/verify-dev-flow-risk.py` と関連する既存検査、差分とリンクの確認。
- 静的検査の成功を実際の AI 行動の証明とは扱わず、未検証事項を記録する。

## 手動確認項目（必要な場合のみ）

- Draft PR の PoC では読み書き権限、レビュー記録の再読、未解決事項と Human 承認の区別を確認する。安全な共有先がなければ実行せず、その事実を記録する。

# 8. 並列実装の判断

## 並列実装

- 不要。

## 判断理由

既存 dev-flow に沿った手順変更で、独立した複数実装案を比較する利益が小さい。

## 設計上の論点

共有媒体の選択を共通フローに固定せず、必要な記録内容だけを定義する。

# 9. レビューで確認してほしいこと

- AI レビューの共有条件と Human の実装承認が混同されないか。
- 版の更新後に差分の再レビューが必要となり、レビュー AI が再確認できない場合は未確認と Human 判断を別に記録できるか。
- Draft PR を推奨候補にとどめ、非 GitHub と Human ローカルレビューの経路が残るか。
- 既存の `review-discipline`、`review-response` と責務が重複しないか。
