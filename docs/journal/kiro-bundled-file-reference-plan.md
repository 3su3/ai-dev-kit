# 1. 概要

## 背景

`harness-sync` は各スキルの `SKILL.md` 本文だけを Kiro の `~/.kiro/steering/` へ生成する。
`SKILL.md` は同梱ファイル（`risk-policy.md` 等）を**相対名**で参照しているが、steering 側には
その実体も所在も無い。

dev-flow v0.2 で分類と承認の本体が `risk-policy.md` / `plan-review.md` へ移ったため、
Kiro では**手順の中核を指す参照が宛先を持たない**状態になっている。

## 目的

Kiro から同梱ファイルへ辿れるようにし、v0.2 の本文を配布する。

## 対応内容

**Kiro 向け生成を Codex と同じ形に揃える。** `SKILL.md` 本文の埋め込みをやめ、
`name` + `description` + **同梱ファイルの絶対パス案内**だけを置く。

いま両者は構造が違う。

| | 配っているもの |
|---|---|
| Codex | 原則の全文 ＋ スキルは name + description + 絶対パス（**本文は含めない**） |
| Kiro（現状） | 原則の全文 ＋ スキルの **`SKILL.md` 本文を全文埋め込み** |

埋め込みを残したままパスを足す折衷も可能だが、**仕組みが2つ残る**。揃えれば
参照切れは構造的に消える（全部がパス経由になる）。

# 3. 現状調査

| 観測 | 結果 |
|---|---|
| Kiro の `dev-flow.md` に「リスク分類」の語 | **0 件**（3日前の v0.1 のまま） |
| 同 `risk-policy` への言及 | 無し |
| Kiro 向け本文の相対参照 | **15 箇所**（8 ファイル） |
| Kiro 向け本文の絶対パス記載 | **無し** |
| Codex 向け `AGENTS.md` の絶対パス記載 | **有り**（`.../claude/skills/<name>/SKILL.md`） |

**Codex は壊れていない。** 同一マシンで絶対パスを辿れる。Issue #2 の 2026-10-18 の実測で
Codex が `risk-policy.md` 等を `cat` した記録があるが、あれは**リポジトリを clone した
作業ディレクトリ内**での読み取りで、`harness-sync` 経由ではない。両者は別の経路。

# 4. 実装方針

**Minimal。** 影響を受けるのは Kiro 向け生成物のみ。

検討した代替。

| 案 | 退けた理由 |
|---|---|
| 埋め込みを残してパスを1行足す | 折衷。Codex と Kiro で仕組みが2つ残る |
| 同梱8ファイルも steering へ配る | steering が 4→12 ファイル。常時読まれる量が増え、①層を小さく保つ方針と衝突 |
| 1ファイルへ連結 | 数百行の単一ファイルになり「必要になったら読む」が成立しない |

## 撤退条件

**Kiro がポインタを辿って実際に読むかは未確認。** Codex には 2026-10-18 の `cat` 実測が
あるが、Kiro には無い。IDE なのでファイルは読めるはずだが、steering の指示だけで
自発的に読むかは別の話。

**失敗は静かに起きる。** Kiro が読まなければ、手順を知らないまま普通に作業を続ける。
エラーは出ない。偽の緑の形そのもの。

下の検証でポインタ到達を確認できなかった場合は、**埋め込み方式へ戻す**（本文の全文埋め込み
＋ 絶対パス案内の折衷案）。その判断は Human に確認する。

# 5. 修正対象

- `bin/harness-sync` — Kiro 向け生成を Codex と同じ形（name + description + 絶対パス）へ変更
- `tests/`（新規または既存へ追記）— パス案内が入ることの検査

対象外: Codex 向け生成、Claude の symlink、`local/`・`terms/`、過去の生成物、
他プロジェクトの設定、`~/.kiro` 以外の環境。

# 6. 影響範囲

- 既存の `~/.kiro/steering/*.md` は上書きされる（`harness-sync` 実行時）
- **Kiro 向けの本文が steering から消える。** 読むには同梱ファイルへ辿る必要がある
- `harness-sync:begin/end` マーカーは維持。Issue #2 の「旧マーカーは互換性のため維持」に従う

### Public-ready との関係

[Public-ready 原則](principles/public-ready.md) は「文書、コード、設定、例、画像、ログ、
リンク先の説明」に適用され、**「エージェントの配布先へ載せない」と配布先まで明示的に
対象にしている**。steering も対象。

その上で、入るのは**マシン依存の絶対パス**であり、機密情報・秘密情報・権利不明の素材の
いずれにも当たらない。`harness-sync` は実行時に `__file__` から算出するため、
**リポジトリにはパスが残らない**。Codex 向けが既に同じ方式を採っている。

# 7. テスト計画

| 検証 | 方法 | 示すこと |
|---|---|---|
| Codex と同じ形になる | 新規テストで生成内容を検査。本文が埋め込まれず、絶対パスが入ること | 構造の一致 |
| frontmatter 検査が生きている | 既存の変異（故意に付けて落ちる） | 安全装置の維持 |
| **Kiro が本文へ到達する** | Kiro で「軽微・通常・高リスクの分類は？」と質問 | **合言葉ではなく本文の中身**に答えられるか |

合言葉は「steering が届く」ことしか示さない。**同梱ファイルへ辿れたか**は、
`risk-policy.md` にしか無い内容を聞いて確かめる。
