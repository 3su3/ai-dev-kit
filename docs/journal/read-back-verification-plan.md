# 実装計画: 外部書き込み後の結果確認

> **状態: 実装済み・レビュー待ち** — [Issue #13](https://github.com/3su3/ai-dev-kit/issues/13) の対応。[Draft PR #14](https://github.com/3su3/ai-dev-kit/pull/14) で実装・検証結果を共有し、実装レビュー待ち。

# 1. 概要

## 背景

外部システムの書き込み API が成功しても、期待した本文や状態が保存されたとは限らない。Issue #13 は、書き込み結果を再取得して初めて本文の不一致を発見できる例を挙げている。

## 目的

後続の判断・処理に影響する書き込みでは、API 応答と保存後の期待状態を区別し、リスクに応じて重要な field を再取得して確かめる。取得不能・不一致を成功と報告しない。

## 対応内容

既存の GitHub 操作手順に、操作ごとの確認対象と、確認できない場合の扱いを短く加える。外部システム一般に通じる判断基準と GitHub 固有の取得方法を混同しない。

# 2. ビジネス向けサマリー

## 変更内容

レビュー投稿・返信・スレッド状態の変更後に、後続の判断に必要な保存状態を確認する手順を明確にする。

## Before / After

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 書き込み成功 | API 呼び出しの手順はあるが、保存後の確認基準はない | 影響に応じて再取得する field を選び、期待値と比較する |
| 取得不能・不一致 | 操作別の扱いがない | 未確認または失敗として記録し、依存する後続処理を止める |

## 業務への影響

GitHub を使うレビュー作業で、投稿できたという応答と、相手に見える内容・状態の一致を分けて扱える。

## 影響しないこと

導入先の承認権限、レビュー文面の事前承認、GitHub 以外の API 実装、全書き込みへの一律の再取得は変えない。

# 3. 現状調査

## 現在の実装

- `CONTRIBUTING.md` は未実測を成功と書かないと定めるが、このリポジトリへの貢献と検証報告の規則である。
- `claude/principles.md` は偽の緑と規約の重複を警戒する。常時読みは増量を避ける設計である。
- `review-discipline/SKILL.md` は GitHub への投稿前の文面承認を求め、同梱 `github.md` は一回の API 呼び出しでレビュー本文とインラインを投稿する手順を持つ。保存後の照合手順はない。
- `review-response/SKILL.md` は指摘の裏どり、返信単位、対応したスレッドだけの resolve を定め、同梱 `github.md` は REST の返信と GraphQL の resolve を示す。保存後の照合手順はない。
- `dev-flow` は Plan・承認・検証報告を扱う。`plan-review.md` は次の担当が Plan 版・指摘状態・承認を再読するよう求めるが、書き込み直後の確認を GitHub 操作全体には定めない。

## 関連する実装

`bin/harness-sync` は既存 skill を各面へ配る。`tests/verify-harness-sync.py` は配布内容を、`tests/verify-review-discipline.py` はレビュー規約の静的整合を確認する。どちらも保存後の GitHub 状態や実作業での遵守は証明しない。クラス・DB・CSS は非該当。

## 問題点

事前の文面承認、API 応答、保存後の内容確認が別の段階であることが操作手順からは分からない。API 成功だけを根拠に「投稿・返信・resolve 済み」と報告する余地がある。

# 4. 実装方針

## 検討事項

どの書き込みに再取得が必要かは、後続の判断・処理が保存内容や状態に依存するか、誤保存時の影響で決める。対象 field と確認強度を操作前に選び、取得不能・不一致は成功と同じ扱いにしない。導入先の規約・承認権限を優先する。

## 方針候補

### 案A

#### 内容

`review-discipline/github.md` と `review-response/github.md` の既存操作に、それぞれ必要な read-back の判断と取得・照合例を短く添える。

#### メリット

実際に書き込む直前に読む操作手順へ届く。新規 kit や常時読みを増やさない。

#### デメリット

外部システム一般の原則を全作業へ配る経路にはならない。共通の判断を両ファイルで繰り返さないよう、操作別の照合対象に絞る必要がある。

### 案B

#### 内容

共通の read-back 文書を新設し、GitHub の二つの手順から参照する。

#### メリット

判断基準を一箇所に置ける。GitHub 以外へ広げる際にも参照しやすい。

#### デメリット

新しい参照先を読む動作が増える。現状の対象操作は二つの同梱手順に限られ、到達性を別に検証する必要がある。

### 案C

#### 内容

現状維持。

#### メリット

文書量と API 呼び出しは増えない。

#### デメリット

既存規則は API 成功と保存後の期待状態を区別する操作手順を与えていない。

## 採用予定の方針

**Minimal、案A。** 影響する二つの GitHub 操作手順に限定する。

## 採用理由

Issue の具体的な到達経路に手順を置ける。GitHub 以外にも成立する判断基準は Plan で境界を説明し、実装文書では GitHub 操作ごとの確認対象を書く。使われない共通文書と新たな Human Gate を増やさない。将来、別の外部操作でも同種の失敗が確認されれば共通配置を再検討する。追加の再取得が軽微な操作まで広がる、または遵守が確認できなければ、対象を絞るか配置を見直す。

# 6. 影響範囲

## 影響を受ける機能

- GitHub レビュー本文・インライン投稿、スレッド返信、resolve の操作手順。

## 影響しない機能

- `claude/principles.md`、`dev-flow`、配布方式、GitHub API クライアント、他リポジトリの規約。

## 想定されるリスク

- **通常リスク。** 認証や API 実装は変えないが、複数の配布面でエージェントの投稿後判断が変わる。再取得を無条件化すると API 負荷が増え、確認失敗を投稿失敗と誤認すると重複投稿も起こりうる。取得失敗時は再投稿を推測で行わず、状態不明として止める。
- 公開文書へ実在の非公開案件の名称・番号・リンク・運用詳細を入れない。

# 7. テスト計画

## Acceptance の検証責任

| Acceptance | 確認内容 | 担当 | 方法 | 適用状態と理由 |
| --- | --- | --- | --- | --- |
| 既存規則との差分・案比較 | Plan の根拠と非採用案 | Human Plan reviewer | 本 Plan と既存規則の差分確認 | required: 設計判断 |
| 公開前提・環境非依存 | 固有情報と環境決め打ちがない | 実装 AI・Human reviewer | 機密・可搬性検査と文書確認 | required: 公開する規約 |
| 重要な書き込みの判断基準 | 後続依存・影響・対象 field・強度が明瞭 | Human reviewer | 二つの操作手順を読む | required: 意味の判断 |
| 取得不能・不一致 | 成功と断定せず依存処理を止める | 実装 AI | 使い捨て環境のシナリオと記録 | required: 重要な振る舞い |
| 不要な API 呼び出し・新 Gate を強制しない | 軽微な操作への一律適用がない | Human reviewer | 文面とシナリオを確認 | required: 運用負荷の判断 |
| Human 承認・Public-ready・実施状況 | Plan 版と承認、検査・未実測の区別 | 実装 AI・Human | Draft PR の記録を確認 | required: このリポジトリの規約 |
| 実装・検証結果を PR に残す | 実測と未実測を分ける | 実装 AI | 同じ PR の本文かコメントを確認 | required: Issue の完了条件 |

## 追加するテスト

### 正常系

- 文書変更のため機械的な TDD は非該当。使い捨て環境で、重要な投稿結果を再取得し、期待する本文・インラインの対象と内容を照合する実作業を可能なら観測する。

### 異常系

- 取得失敗と保存内容の不一致を区別し、どちらも成功と断定せず後続の依存処理を止めるシナリオを確認する。実 API を使えない場合は模擬と明記する。

### 境界値

- 後続の判断に影響しない軽微な書き込みまで一律に再取得しないこと、確認失敗時に推測で再投稿しないことを確認する。

## リグレッション確認

- README「検証」の適用可能な静的検査、`python3 bin/harness-sync --verify`、差分の手動確認。配布先未同期なら `--verify` の失敗を未到達として記録する。道具を追加する場合のみ変異で赤になることも確かめる。

## 手動確認項目

- 「文書に書いた」「エージェントへ届いた」「守られた」を別に記録し、未実測は理由と代替確認を添える。実操作の確認には使い捨てリポジトリだけを用いる。

## 検証の順序

`dev-flow/SKILL.md` の共通デフォルトに従う。Phase 0 は不要。Plan・Human 実装承認の後に文書を変更し、静的検査と差分確認、可能なら使い捨て環境での到達・遵守確認、レビューの順に進める。
