## 長い対話での発火（2026-10-16）

上の発火の測定は**単発セッション**で取ったもので、長い対話では測っていなかった。
同一セッションを `--resume` で継いで5ターン測った。

| ターン | 入力 | 発火 |
|---|---|---|
| 1 | リポジトリの要約 | — |
| 2 | 「実装して直して」 | **dev-flow** |
| 3 | 雑談 | — |
| 4 | 「レビューして」 | **—** |
| 5 | 「別の箇所も直して」 | **—** |

**②層はセッションの入り口で1回効くだけで、セッション中ずっと効き続けはしない。**
単発では確実に発火する「レビューして」が、4ターン目では発火しない。

### 主張の範囲

「『レビューして』で発火する」は、**そのセッションで最初にその種の依頼が来たとき**に限る。
長い作業の途中で種類が変わっても読み直されない。規律を効かせたいなら
セッションを分けるか、①層（毎回読まれる）側に置く。

これは `review-discipline` が元々「レビューは実装とは別セッションで行う」と
書いていることと整合する。別セッションにする理由が1つ増えた
（白紙の視点を得るためだけでなく、**規律が実際に読まれるため**）。

### 既存セッションの途中で効くか（2026-10-16）

| 層 | 途中で効くか | 根拠 |
|---|---|---|
| ① `principles.md`（`@` import） | **効かない** | セッション開始時に確定する。追記した会話の文脈に入らなかった |
| ② スキルの追加 | 効く | 作った直後に利用可能一覧へ現れた |
| ② スキルの編集 | 効く | 呼び出し時にファイルを読むため、数分前の追記が入った版が返った |
| ② スキルの自動発火 | **最初の該当依頼のときだけ** | 5ターン測定（上記） |
| ③ `bin/` の道具 | いつでも | 通常のコマンド |

**①を変えたら新しいセッションを開く。** 変えた当人のセッションには効かないので、
「書いたから効いているはず」と思い込みやすい。

**②は途中から効かせたいなら名指しで呼ぶ。** 自動発火は入り口の1回だけなので、
作業の種類が変わったときは `<スキル名> で見て` のように指定する。

> スキルの編集が効くことは**手で呼び出して**確かめた。自動発火の経路でも
> 最新版が読まれるかは測っていない（同じファイルを読む作りなので同じはずだが、未測定）。

## review-response（レビュー指摘への対応）の機構（2026-10-16）

スキルにコマンドを書く前に、実機（検証用 private リポジトリの PR）で通した。

| 操作 | 実体 | 結果 |
|---|---|---|
| スレッド一覧 | GraphQL `reviewThreads` | `threadId` と先頭コメントの `databaseId` が引ける |
| 返信 | REST `POST /pulls/{n}/comments` + `in_reply_to` | 投稿される |
| resolve | GraphQL `resolveReviewThread` | `isResolved: true` になる |
| unresolve | GraphQL `unresolveReviewThread` | **戻せる** |
| 返信の削除 | REST `DELETE /pulls/comments/{id}` | 消せる。ただし**通知は取り消せない** |

**resolve に REST の口は無い。** 返信は REST、resolve は GraphQL で、別の API を跨ぐ。

**resolve は可逆、返信は不可逆**（消しても相手には既に届いている）。
文面の承認が要るのは返信のほうで、resolve は後から戻せる。

### 測定が静かに落ちていた（2026-10-16）

`review-response` の発火を3入力で測ったとき、シェル側で `grep "発火したツール"` に
絞っていたため、**2件が失敗しているのに「出力なし」としか見えなかった**。
プローブ自身も、失敗時は `sys.exit(メッセージ)` で stderr へ書くだけだった。

**取得失敗と「発火なし」が同じ顔になっていた。** これは2度目（最初は `timeout` が
macOS に無くコマンドが起動していなかった件）。

直したこと。

- プローブは失敗時も**必ず `発火したツール: !! ...` の行を標準出力に出して**終了コード 2 で落ちる
- タイムアウトと `OSError`（`claude` が PATH に無い等）を個別に捕まえる
- 故意に失敗させて、黙らないことを確認した

### harness-status の差分は全セッションを含む（2026-10-16）

差分に出た4件のうち2件が自分の書いたものでなかったため、**一度「測定（`claude -p`）が
memory を汚した」と判断したが、誤りだった。** 出どころを確認したところ、
別セッション（`originSessionId` が異なる）が書いたもので、本文も別チケットの作業だった。
同時に 10 個のセッションが動いていた。

**差分は、並行して動いている全セッションの memory を含む。** これは欠陥ではなく
そうあるべき挙動（引き上げの判断は、どのセッションで気づいたかに依らない）。

運用上の注意。

- 「増えた」件数は、**自分がそのとき何をしていたかと一致しない**
- `[N回]` 付きで出たものは、別の作業で踏んだ再発かもしれない

**原因を決めつける前に出どころを確認する。** 自分の作業と時刻が重なっていることは、
自分が原因である根拠にならない。

## 判定ルールの変更（2026-10-16）

`issue:` が無いときの判定を `COMMENT` から `APPROVE` へ変えた。

**理由はラベルと機構の食い違い。** `suggestion:` / `nit:` は定義として「止めない」もの
なのに、`COMMENT` は承認を与えないため、ブランチ保護が approval を要求するリポジトリでは
**実質ブロックしていた**。判断を含む指摘は原理的に尽きないので、尽きないもので承認を
保留しない。

| 条件 | 判定 |
|---|---|
| `issue:` が1件以上 | `REQUEST_CHANGES` |
| `issue:` なし・未解決の `question:` あり | `COMMENT` |
| それ以外 | `APPROVE` |

`question:` だけ例外に残した。判断がつかないから聞いている状態で `APPROVE`（＝懸念なし）を
出すのは信号として嘘になるため。

### 実測

| 入力 | 判定 |
|---|---|
| `suggestion:` 2 + `nit:` 1、`issue:` 0 | **`APPROVE`**（変更前は `COMMENT`） |
| `suggestion:` 1 + 未解決の `question:` 1、`issue:` 0 | **`COMMENT`** |

**この測定が示す範囲。** ルールを読めていることは示すが、実際のレビューで指摘を
正しく `issue:` / `suggestion:` へ分類するかは示さない。分類の妥当性は別の問題。

### 実 PR での測定は成立しなかった

検証用 PR で測ろうとしたが、レビュアーが `issue:` を2件見つけたため
`REQUEST_CHANGES` になり、**変更した経路（issue ゼロ）を通らなかった**。
代わりに次の2つが確認できた。

- 自分の PR では `COMMENT` にし、本来の判定を本文の冒頭に書く
- テストを実行できなかったとき、「通った」と書かずに**実行できていないと明記する**

## Kiro への配布方式（2026-10-19）

**ポインタ方式は Kiro では成立しない。本文を埋め込む。**

Codex 向け `AGENTS.md` と同じく「本文は `<絶対パス>/SKILL.md` にある」とだけ置いたところ、
Kiro は辿らず**一般知識で答えた**。

| 方式 | 「軽微・通常・高リスクで何が必要？」への回答 |
|---|---|
| ポインタのみ | `blast radius` / 可逆性 / リンター / 依存パッケージ。**正本に1語も無い語彙**。承認の扱いが正本と**逆** |
| 本文を埋め込み | 「承認権限を付与・省略するものではない」「APIを利用できることは操作の承認を意味しない」等、**正本の本文と一致** |

## 常時読みを増やすと、指示の遵守が落ちる（2026-10-21）

**ハーネスの ①層が「増やすと全部の効きが落ちる」と書いている通りのことが、実測で出た。**

### きっかけ

Kiro の実作業（対象リポジトリ）で `dev-flow` の方針宣言が **3 本中 0 本**。
到達は確かめてある（合言葉で4本すべて届く。プロジェクト steering が同時に載る実条件でも同じ）。
メタで聞くと `Minimal / Pattern / Robust` と即答する。**知っていて、やらない。**

### 切り分け

同じ課題（「`fee()` に、金額が負のときは 0 を返す処理を足して。実装して。」）を、
**ユーザー階層の steering は同一のまま**、対象リポジトリの steering の有無だけ変えて各6回。

| | 方針を宣言 | TDD（先にテスト） | 応答の長さ（平均） |
|---|---:|---:|---:|
| プロジェクト steering 無し | **6/6** | **6/6** | 1,377 字 |
| プロジェクト steering 有り（+9,870 字） | **2/6** | **1/6** | 866 字 |

実作業は 0/3 で、この傾向の延長にある。

**プロジェクト steering には「宣言するな」も「TDD をやめろ」も書いていない。**
競合ではなく**希釈**。常時読みを 9,870 字足しただけで、無関係な2つの指示が同時に落ちた。

### 面ごとの常時読みの量

| 面 | 常時 | 条件付き |
|---|---:|---:|
| Claude | **1,089 字**（`CLAUDE.md` 経由の ①層） | 6,662 字（description 一致で発火） |
| Kiro | **8,358 字**（steering 全部） | 無し |

**Kiro には条件付きの仕組みが無い。** `inclusion: manual` / `fileMatch` はあるが、
「実装してと言われたら」のような**依頼の種類**では引けない。

対象リポジトリで作業すると、ここにプロジェクトの 9,870 字が足されて **18,228 字**になる。

### 読み取れること

- **ハーネスの Kiro 面は、ハーネス自身の ①層に違反している。** 8,358 字を常時背負わせている
- 実装中に `review-discipline` / `review-response`（4,995 字）は要らない。Claude では載らない
- 落ちたのは宣言だけでなく TDD も。**特定の指示の問題ではなく、量の問題**
- 応答が短くなっている（1,377 → 866 字）。調査もテストも減っている

### 測り方の注意

- **分母を「ファイルを書いたセッション」にしない。** レビューでも記録を書くので混ざる。
  8 本中 4 本は「レビューして」だった。依頼文で絞る
- 判別子は `Minimal` / `Pattern` / `Robust`。対象リポジトリのどこにも無く、`strategies.md` にしかない
- TDD を第2の判別子に置いた。**1つの指示だけで見ると「その指示が弱い」で終わる**

### ハーネス側だけで戻せる

実装中に要らないもの（`review-discipline` / `review-response`、合わせて 4,995 字）を
ユーザー階層から外し、**プロジェクト steering はそのまま**で同じ課題を6回。

| 条件 | ユーザー階層 | プロジェクト | 合計 | 宣言 | TDD |
|---|---:|---:|---:|---:|---:|
| プロジェクト無し | 8,358 | 0 | 8,358 | **6/6** | **6/6** |
| プロジェクト有り | 8,358 | 9,870 | 18,228 | 2/6 | 1/6 |
| **レビュー系を外す** | **3,363** | 9,870 | **13,233** | **5/6** | **4/6** |

**自分の側の 4,995 字を外すだけで、2/6 → 5/6、1/6 → 4/6 に戻る。**
対象リポジトリの steering には一切触れていない。

### 配り分ける手段 ─ `resources` は「足す」であって「絞る」ではない

Kiro の agent 定義（`~/.kiro/agents/<name>.json`）に `resources` がある。
最初これを「読むものを絞れる」と読んだが、**絞れない。**

| 測ったこと | 結果 |
|---|---|
| `resources` に2本だけ書いたエージェントで、steering の合言葉4つを聞く | **4つとも返る** |
| そのエージェントが実際に適用されたか | **適用された**（存在しない名前は `Mode not found` でエラーになる） |
| steering の**外**に置いたファイルを `resources` で指すと届くか | **届く**（対照の既定エージェントは `NONE`） |

**`~/.kiro/steering/` は、どのエージェントでも無条件に全部載る。** `resources` はそこへ**足す**だけ。

したがって配り分けの形はこうなる。

```
~/.kiro/steering/          ← 常時要るものだけ（00-principles + dev-flow = 3,363 字）
~/.kiro/harness-parts/     ← steering の外。常時は載らない
~/.kiro/agents/review.json ← resources で harness-parts の2本を足す
```

`kiro-cli chat --agent review` / Orca の `--agent <id>` で選ぶ。
**これが Claude の「description 一致で発火」に相当する、Kiro 側で唯一効く条件付き機構。**
`inclusion: manual` / `fileMatch` は依頼の種類では引けない。

**欠点: 自動では切り替わらない。** Claude は「レビューして」で勝手に発火するが、
Kiro は人がエージェントを指定する必要がある。指定を忘れるとレビュー規約が載らない。

## steering の枠を review-discipline へ差し替えた（2026-10-21）

### 根拠は使用頻度と Orca の制約であって、遵守の改善ではない

**したがって「差し替えで遵守が上がる」とは言えない。** 言えるのは次の2つ。

- 使用の多い側に規約を置いた（Orca から agent を選べない以上、これが唯一の選択）

## レビューを飛ばして検証環境へ反映した（2026-10-26）

実作業で次の順に進んだ。

```
Draft → （レビューなし）→ 検証環境へ反映・検証 → PR 本文更新
```

本来は `Draft → セルフレビュー → Ready → AI レビュー → 検証環境`。
**セルフレビューも AI レビューも一度も通らないまま、検証環境へ出た。**

### 文言は足してあったのに効かなかった

2026-10-23 に2つ足していた。**どちらも「順序が定義されている」前提だった。**

| 足したもの | なぜ効かなかったか |
|---|---|
| `plan-template.md` の「検証の順序」 | **その節を持つ計画を書いたときだけ**効く |
| `implementer.md` の「まだ順番が来ていない工程を持ち出さない」 | 「**計画が定めているなら**」という条件付き。計画に無ければ自由と読める |

### 本当の穴は、段が存在しなかったこと

`SKILL.md` の「順番」は5段で終わっており、**検証環境への反映が段として無かった。**

```
1 調査 → 2 計画 → 3 承認 → 4 実装 → 5 レビュー
                                      ↑ ここで終わり
```

段が無いので、**どこに置くべきかの基準が存在しない。** 「飛ばした」とすら判断できない。

### 直したもの

1. **順番に 6 を足した** — 検証環境への反映と実機確認。5 が通ってから
2. **手を止める線に足した** — レビューを経ていない実装を検証環境へ反映しない。
   **利用者が選べる形で提案することもしない**（選択肢に出した時点で順番は崩れる）
3. **`implementer.md` の計画頼みをやめた** — 「計画に書かれていなくても既定がある」

**2 が要るのは、実際には「選択肢として提示して選んでもらった」形だったため。**
「聞かない」だけでは、選択肢に並べる形で回避される。

### 装置にした

`verify-dev-flow-risk.py` に4つ足した。文言が消えたら赤になる（変異で確認）。

- `SKILL.md` に検証環境の段があること
- `SKILL.md` に未レビュー反映の停止条件があること
- `implementer.md` が既定を計画頼みにしていないこと
- `implementer.md` が「選択肢としても出さない」を持つこと

**これは配布物の検査であって、実際に止まるかは示さない。** 次に同じ場面が来たときに測る。

### 最初の直しは、自分の流儀を普遍として書いていた

「実機はレビューが通ってから」と `SKILL.md` に書いたが、**これは流儀。**
逆順が成立する運用がある。

- レビュアーに**動いている画面**を見せないと判断できない
- **反映前後のキャプチャ比較**が要る（対象リポジトリ側にそういう検証スキルがあった）

普遍なのは次の3つだけだった。

| | 普遍か |
|---|---|
| 実機での確認が**段として存在する** | **普遍**（どの順かは決めない） |
| 決まっている順番を**自分の判断で前後させない** | **普遍** |
| まだ来ていない工程を**選べる形で提案しない** | **普遍** |
| 実機は**レビューの後** | **流儀** → `local/preferences.md` へ |
| そもそも**検証環境がある** | **環境依存** |

検査も組み替え、**順序を普遍として書き戻したら赤になる**ものを足した
（`SKILL.md hardcodes one team's ordering as universal`）。

### 変異の片付けで、自分の変更を消した

`git checkout -- <file>` で変異を戻したとき、**同じファイルの未コミットの本来の変更も消えた。**
テストが「さっきまで PASS だったのに NG」になって気づいた。

**コミットしてから変異を当てる**（既に原則として書いてあったのに、またやった）。

### 道具の限界がひとつ増えた

その9件のうち `[issue]` 1件は、**チャットで「別 PR で直す」と共有されていた。**

`bin/review-outcomes` は **GitHub のレビュースレッドしか見ない。**
チャットや口頭での合意は「無反応」に見える。
**「無反応」を「無視された」と読んではいけない。** 道具の出力にもこの限界を書いた。
