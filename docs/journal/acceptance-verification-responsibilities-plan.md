# 実装計画: Acceptance の検証責任を dev-flow に加える

> **状態: 実装済み・実装レビュー待ち** — PR #9 の[Human実装承認](https://github.com/3su3/ai-dev-kit/pull/9#issuecomment-6544503281)を受け、同じ Draft PR で実装した。mergeは未承認。

# 1. 概要

## 背景

Acceptance Criteria の確認を誰が担うか曖昧だと、機械で判定できる動作を Human に再テストさせたり、実機固有の確認をブラウザーエミュレーションだけで済ませたりする。導入元の検証責任の分類から、導入先を限定しない判断手順だけを還元する。

## 目的

Acceptance ごとに「誰が・何を・どう確認するか」と required / not applicable の理由を計画できるようにする。

## 対応内容

既存 `dev-flow` の検証手順と Plan テンプレートを小さく拡張する。Gate 名、順番、承認権限は導入先の規約に委ねる。

# 2. ビジネス向けサマリー

## 変更内容

検証可能な振る舞い、Human の体験・意味判断、端末・権限・実ネットワーク等に依存する確認を、各 Acceptance に応じて割り当てる。

## Before / After

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 検証計画 | テスト・Lint・静的解析と実機確認の記載が中心 | Acceptance 単位で確認内容、担当、方法、適用理由を記載 |
| 環境依存確認 | `実機での確認` の段はある | 必要性を個別に判断し、適切な担当と環境を選ぶ |

## 業務への影響

導入先での計画・検証報告の明確化。軽微な変更に一律の新しい手作業は課さない。

## 影響しないこと

導入元プロジェクトのフロー、導入先の承認・レビュー・merge 権限、配布設定は変更しない。

# 3. 現状調査

## 現在の実装

`risk-policy.md` はリスク別の検証強度と未実施の記録を定め、`SKILL.md` は実機確認の段と対象リポジトリによる順番の決定を定める。`workflow.md` はテスト・Lint・静的解析を扱う。`plan-template.md` のテスト計画には正常・異常・境界・手動確認があるが、Acceptance と担当の対応はない。また同テンプレートの「検証の順序」は実機確認の位置を既定として固定しており、`SKILL.md` の導入先優先と整合しない。

## 関連する実装

`verification-report.md` は実機確認後の報告形式。`tests/verify-dev-flow-risk.py` は静的な規約整合性と負例を検査する。`CONTRIBUTING.md` は公開可能性、可搬性、Draft PR と Human 実装承認を要求する。クラス・API・DB・CSS は対象外。

## 問題点

既存の検証項目からは「期待結果を機械で判定できるか」「Human の判断が必要か」「特定環境に依存するか」と担当・方法・非該当理由を再構築できない。

# 4. 実装方針

## 検討事項

分類を新しい独立 kit にするか、既存のリスク別検証に重ねるか。環境依存確認の担当を Human 固定にしないこと。導入先の順番と承認を維持すること。

## 方針候補

### 案A

#### 内容

既存 `dev-flow` に短い判断手順を加え、Plan の検証欄で Acceptance ごとの責任を記録する。

#### メリット

調査・Plan・検証の既存経路を使い、導入先の規約に合わせられる。

#### デメリット

実際の担当・方法は導入先で決める必要がある。

### 案B

#### 内容

特定プロジェクトと同じ三つの Gate と順序を持つ独立 kit を追加する。

#### メリット

特定プロジェクトと同じ運用では書き方が揃う。

#### デメリット

他のプロジェクトへ固有の役割・順番を強制し、正本も増える。

## 採用予定の方針

**Minimal、案A。** 既存の `dev-flow` に限定する。単一の判断手順を規約の正本とし、入口・テンプレートはその参照と記録欄に絞る。

## 採用理由

依頼元の変更境界と `CONTRIBUTING.md` の可搬性に一致する。既存のリスク分類や承認ゲートを置き換えない。

# 6. 影響範囲

## 影響を受ける機能

- `dev-flow` を使う実装計画と検証報告。

## 影響しない機能

- `review-discipline`、`review-response`、配布スクリプト、他リポジトリの規約。

## 想定されるリスク

- 共通ハーネスの手順変更なので**高リスク**。一律の Human・実機 Gate が追加されたように読まれる危険がある。
- テンプレートが長くなり、軽微な変更にも過剰な Plan が要求される危険がある。
- 選択した責任分類だけで Product semantics や Human 承認を判断したように読まれる危険がある。
- 撤退条件: 使い捨て環境のエージェント検証で上記の誤解が繰り返される場合は、この拡張を採用せず Plan へ戻る。

# 7. テスト計画

## 追加するテスト

### 正常系

- 静的検査で判断手順への参照、Acceptance ごとの担当・内容・方法・適用理由の記録欄を確認する。

### 異常系

- 規約の核心を一つ壊し、検査が赤になることを確認する。一律の Human 専属・実機必須・固定順序を許さないことを確認する。

### 境界値

- 軽微な変更では過剰な Plan を要求しないこと、分類不能・Product semantics に関わる判断では導入先の Human 判断に戻すことを確認する。

## リグレッション確認

- README の「検証」にある適用可能な既存検査、差分確認、Public-ready / 可搬性確認。

## 手動確認項目

- 使い捨て環境の新規エージェントセッションで、機械判定可能・体験判断・環境依存・非該当の例を与え、実際の応答を確認する。到達と遵守を区別し、未実測は未実測と記録する。

## 検証の順序

Plan 承認後に文書・静的検査を実装し、セルフレビューを行う。その後、使い捨て環境でエージェント挙動を確認する。実機配布は行わない。導入先の一般的な検証順序は規定しない。

# 8. 並列実装の判断

## 並列実装

- 不要。

## 判断理由

既存スキル内の一つの責務分類であり、独立案の比較に利益が小さい。

## 設計上の論点

- 正本を一箇所にし、入口とテンプレートに必要最低限だけ反映する。

# 9. レビューで確認してほしいこと

- 特定プロジェクト固有の Gate 名・順序・担当を他リポジトリに強制していないか。
- `plan-template.md` の既定順序を解消することがこの変更の範囲として妥当か。
- 適用理由の記録が軽微な変更に過剰な負荷を与えないか。

## Plan レビューの経路と記録

ai-dev-kit の Draft PR で Human Plan Review を受ける。対象版は Plan のコミット permalink とし、指摘・対応・承認は同 PR Conversation に残す。AI レビューを依頼した場合は `plan-review.md` に従い対象版と再確認結果を記録する。
