# 実装計画: Acceptance の検証責任を dev-flow に加える

> **状態: 追加実装済み・実装再レビュー待ち** — 改訂Plan `93a4435` への[Human追加実装承認](https://github.com/3su3/ai-dev-kit/pull/9#issuecomment-6565303429)を受け、後方互換性の修正と使い捨て環境での検証を行った。blocking findingの解消認定とmergeは未承認。

# 1. 概要

## 背景

Acceptance Criteria の確認を誰が担うか曖昧だと、機械で判定できる動作を Human に再テストさせたり、実機固有の確認をブラウザーエミュレーションだけで済ませたりする。導入元の検証責任の分類から、導入先を限定しない判断手順だけを還元する。

## 目的

Acceptance ごとに「誰が・何を・どう確認するか」と required / not applicable の理由を計画できるようにする。

## 対応内容

既存 `dev-flow` の検証手順と Plan テンプレートを小さく拡張する。検証順序は従来の共通デフォルトを維持し、導入先が明示した規約・計画を優先する。Gate 名と承認権限は導入先に委ねる。

# 2. ビジネス向けサマリー

## 変更内容

検証可能な振る舞い、Human の体験・意味判断、端末・権限・実ネットワーク等に依存する確認を、各 Acceptance に応じて割り当てる。

## Before / After

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 検証計画 | テスト・Lint・静的解析と実機確認の記載が中心 | Acceptance 単位で確認内容、担当、方法、適用理由を記載 |
| 環境依存確認 | `実機での確認` の段はある | 必要性を個別に判断し、適切な担当と環境を選ぶ |
| 検証順序 | 共通テンプレートに既定順序とPhase 0例外がある | 同じ順序を未指定時のフォールバックとして維持し、明示的な導入先指定を優先 |

## 業務への影響

導入先での計画・検証報告の明確化。軽微な変更に一律の新しい手作業は課さない。

## 影響しないこと

導入元プロジェクトのフロー、導入先の承認・レビュー・merge 権限、配布設定は変更しない。

# 3. 現状調査

## 現在の実装

承認前の `plan-template.md` にはテスト・Lint・静的解析 → セルフレビュー → AI/Humanレビュー → 実機確認の既定順序と、実装前のPhase 0例外があった。現行head `5fb0ce8` はAcceptanceの記録欄を加えた一方、この既定順序を削除した。`SKILL.md` は実機確認の段を示すが実施時期を導入先に委ね、`implementer.md` は計画に順序がなくても既定があると述べる。導入先の明示順序がない場合の規則が不一致になっている。

## 関連する実装

`verification-report.md` は実機確認後の報告形式。`tests/verify-dev-flow-risk.py` は静的な規約整合性と負例を検査する。`CONTRIBUTING.md` は公開可能性、可搬性、Draft PR と Human 実装承認を要求する。クラス・API・DB・CSS は対象外。

## 問題点

Acceptanceの責任分類は現行headで追加済み。ただし、ローカルに検証順序の指定を持たず旧テンプレートの既定に依存する導入先では、現行headへの更新後に順序が未定義となり、従来の工程がHuman確認待ちになる可能性がある。CI成功と一つの架空Acceptance分類の実測では、この後方互換性を確認できていない。

# 4. 実装方針

## 検討事項

Acceptance分類を既存フローへ重ねる方針は維持する。今回の再検討は、従来の検証順序を未指定時のデフォルトとして保ち、導入先の明示指定・意図的な無効化・Phase 0例外と両立させる方法に限定する。

## 方針候補

### 案A

#### 内容

既存 `dev-flow` に短い判断手順を加え、Plan の検証欄で Acceptance ごとの責任を記録する。

#### メリット

調査・Plan・検証の既存経路を使い、導入先の規約に合わせられる。

#### デメリット

実際の担当・方法は導入先で決める必要がある。

### 案B

#### 内容

特定プロジェクトと同じ三つの Gate と順序を持つ独立 kit を追加する。

#### メリット

特定プロジェクトと同じ運用では書き方が揃う。

#### デメリット

他のプロジェクトへ固有の役割・順番を強制し、正本も増える。

## 採用予定の方針

**Minimal、案A。** 既存の `dev-flow` に限定する。単一の判断手順を規約の正本とし、入口・テンプレートはその参照と記録欄に絞る。

## 採用理由

依頼元の変更境界と `CONTRIBUTING.md` の可搬性に一致する。既存のリスク分類や承認ゲートを置き換えない。

## 検証順序の後方互換性: 比較と採用予定

| 案 | 方法 | 利点 | 欠点・判断 |
| --- | --- | --- | --- |
| 既存規約から参照 | `SKILL.md` の既存の「順番」を共通デフォルトの正本として明確化し、`plan-template.md` と `risk-policy.md` から参照する。導入先の明示規約・計画が優先 | 新規ファイルを増やさず、テンプレートを使わない軽微変更でも読める。従来の順序とPhase 0を保てる | 既存の「ここでは順番を決めない」という文面を改め、参照元との整合確認が必要。**採用予定** |
| 独立したデフォルト設定ファイル | 新規ファイルに順序と優先順位を置き、各入口から参照する | 順序だけを独立して読める | ファイルと参照経路が増え、既存規約との二重管理を招きやすい。現時点で独立させる必要がないため不採用 |
| 共通デフォルトを廃止 | 現行headのように順序を導入先だけに委ねる | 共通規約が少ない | 既存利用者の未指定時の挙動を変える。対象導入先の棚卸し・移行手順・Humanの破壊的変更承認が必要で、このIssueの境界を超えるため不採用 |

**Minimal、既存規約参照案。** 共通デフォルトは、テスト・Lint・静的解析 → セルフレビュー → AI/Humanレビュー → 必要な実機確認とする。前提確認が実装方針を左右するときは、実装前のPhase 0に置き、通過条件を記録する。実機確認の要否はAcceptanceごとに判断し、不要な工程は追加しない。

導入先の `AGENTS.md` / `CLAUDE.md` 等の明示規約と承認済みPlanで別の順序を指定する場合はそちらを優先する。個人設定は導入先規約に優先しない。**指定がない**場合は共通デフォルトを適用し、**明示的な無効化**では理由と代替順序または非該当の工程を記録する。無効化だけが書かれ代替が不明、または規約が競合する場合はHumanに確認して停止する。承認・レビューの要否そのものを順序の上書きで省略しない。

# 6. 影響範囲

## 影響を受ける機能

- `dev-flow` を使う実装計画と検証報告。

## 影響しない機能

- `review-discipline`、`review-response`、配布スクリプト、他リポジトリの規約。

## 想定されるリスク

- 共通ハーネスの手順変更なので**高リスク**。一律の Human・実機 Gate が追加されたように読まれる危険がある。
- 既存導入先が使う共通の既定順序を失うと、従来の工程が停止する。反対に導入先の明示順序より共通デフォルトを優先すると、導入先の運用を壊す。
- テンプレートが長くなり、軽微な変更にも過剰な Plan が要求される危険がある。
- 選択した責任分類だけで Product semantics や Human 承認を判断したように読まれる危険がある。
- 撤退条件: 使い捨て環境で未指定時の旧順序、明示上書き、Phase 0のどれかが再現できない場合は、順序変更を適用せずPlanへ戻る。

# 7. テスト計画

## 追加するテスト

### 正常系

- 静的検査で判断手順への参照、Acceptance ごとの担当・内容・方法・適用理由の記録欄を確認する。
- ローカルの順序指定がないとき共通デフォルトが有効であり、明示指定があるときだけ上書きされることを確認する。

### 異常系

- 規約の核心を一つ壊し、検査が赤になることを確認する。一律の Human 専属・実機必須を許さず、旧順序の削除、明示指定の無視、未指定と無効化の混同を検出する。

### 境界値

- 軽微な変更では過剰な Plan を要求しないこと、分類不能・Product semantics に関わる判断では導入先の Human 判断に戻すことを確認する。
- Phase 0で実装前の前提確認を行うとき、通過条件を記録し、通常の順序へ戻れることを確認する。

## リグレッション確認

- README の「検証」にある適用可能な既存検査、差分確認、Public-ready / 可搬性確認。

## 手動確認項目

- 使い捨て環境の新規エージェントセッションで、機械判定可能・体験判断・環境依存・非該当の例を与え、実際の応答を確認する。到達と遵守を区別し、未実測は未実測と記録する。
- 別の使い捨て環境で、順序指定なし・導入先の明示上書き・Phase 0の各ケースを新規セッションで実測する。対象の規約へ到達した証拠と、出力が各順序を守った証拠を分けて記録する。明示無効化に代替順序がない場合は停止することも確認する。

## 検証の順序

本Planの再承認後に文書・静的検査を修正し、セルフレビューと使い捨て環境のエージェント挙動を確認する。実機配布は行わない。導入先に明示指定がない場合の共通デフォルトは上記の旧順序を維持する。
