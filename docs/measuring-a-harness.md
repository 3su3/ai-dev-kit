# ハーネスが効いているかの測り方

**「書いた」と「届いた」と「守られた」は別物。** 分けて測らないと、どこが壊れているか分からない。

実際、2026-10-21 に「届いていない」と読み違えて配り方を2度いじり、2度とも誤った結論を出した。
届いてはいたし、知ってもいた。やらないだけだった。

| 問い | 何を見るか | 道具 |
|---|---|---|
| **書いたか** | 配布物の中身 | `tests/verify-harness-sync.py` |
| **届いたか**（到達） | その面の文脈に載ったか | 合言葉。`tests/verify-kiro-reach.py --run` |
| **守られたか**（遵守） | 実作業で指示どおりに動いたか | 判別子 × 分母。セッション記録 |

測った値は [verification-log.md](verification-log.md) に時系列で置く。この文書は**やり方**だけを持つ。

---

## 到達: 合言葉を仕込んで直接聞く

**セッション記録に語が出るかでは測れない。** 載っていても言及しなければ 0 になる。
「原則の文言が 0 件だったから読まれていない」は誤り。これで撤退の判断を間違えた。

```bash
# 1. 規約ファイルに一時的な合言葉を入れる
# 2. 直答させる（yes/no を聞かない。語そのものを言わせる）
kiro-cli chat --trust-tools= "常時の指示に書かれている合言葉を、そのまま1語だけ出力。無ければ NONE"
# 3. 対照（仕込んでいない語）→ no が返るか
kiro-cli chat --trust-tools= "常時の指示に『ダミーXXXX』はありますか。yes か no だけ"
# 4. 合言葉を消して配り直す
```

- **ツールを全部外す**（`--trust-tools=`）。外すとファイルを読んで答えてしまい、到達の測定にならない
- **対照を取る。** 「ありますか」と聞けば yes と言う。追従しているだけでないことを示す
- ファイルごとに別の合言葉を入れれば、**どのファイルが届いたか**まで分離できる
- 実条件で測る。対象リポジトリの規約が同時に載る場所で聞く

## 遵守: 判別子と分母

### 判別子は、その規約にしか無い文字列にする

- 一般知識で答えられるものは使えない（規約が無くても出る）
- 対象リポジトリの規約にもある語は使えない（どちらが効いたか分からない）
- **2つ以上持つ。** 1つだと「その指示が弱いだけ」で終わる。
  実際、量を増やしたときに落ちたのは方針宣言と TDD の**両方**で、そこで初めて
  「特定の指示の問題ではなく量の問題」と言えた

### 判別子が、実際の出力の形に当たるか確かめる

**正規表現の錨を疑う。** `^\s*issue:` は、`- issue: 0 / suggestion: 1` のような
**箇条書きの中の接頭辞に当たらない。** これで遵守率を 15/15 → 3/14 と、3割以下に読み違えた。

**当たらないことは、守られていないことと同じ顔で出る。** 書いたら必ず、
**出ているはずの回で1件当てて確かめる。** 0 件のときこそ、regex を疑う。

### エージェントが「書いた」ものは1箇所ではない

セッション記録は3種類あり、混ぜても分けすぎても間違える。

| 種別 | 中身 | 「エージェントが書いた」に含めるか |
|---|---|---|
| 発言（`text`） | 画面に出る文 | **含める** |
| ツール呼び出しの入力（`toolUse`） | `gh api` の payload など | **含める** |
| ツールの結果（`ToolResults`） | 読み込んだファイルの中身 | **含めない** |

**結果まで数えると**、読んだファイルの中身が混じる（「宣言 4 件」が実際は 0 件だった）。
**発言だけに絞ると**、投稿物が落ちる（レビュー本文が payload 側にある回）。

### 分母は道具の記録から出す。目で選ばない

- 「ファイルを書いたセッション」を実装の分母にしない。**レビューでも記録は書く。**
  これで 8 本中 5 本がレビューなのに実装として数えられ、**残り 3 本が分母になった**
- 「全セッション」も分母にしない。調査も雑談も入る
- **分母は2回続けて間違えた。** 直したつもりの値も間違っていることがある

  | 何を分母にしたか | 割合 | 何が混ざっていたか |
  |---|---|---|
  | 全セッション | 16% | レビュー・調査・雑談 |
  | `Edit` を呼んだセッション | 46% | **レビューも記録を書く** |
  | 依頼文が実装を頼んでいるもの | 43% | — |

  （2026-10-21 時点。**セッションが増えるたび動くので、値は書き写さず数え直す**）

  **2行目に注意。** 割合は3行目とほぼ同じなのに、**中の顔ぶれが違う。**
  レビュー依頼が1本混ざっていたうえに、**実装依頼の半分以上を取りこぼしていた**
  （13 本と 30 本）。ファイルを書かずに終わった回、別の手段で実装した回が落ちる。

  **率が合っているから分母が正しい、とは言えない。件数ではなく集合を見る。**
  混入（入ってはいけないものが入る）と取りこぼし（入るべきものが落ちる）は別で、
  **率だけ見ていると打ち消し合って気づけない。**

  最後は依頼者自身の言葉で絞っている。**自分で括り直していない**のがここだけ
- セッション記録は `Prompt` / アシスタントの発言 / ツール結果が混ざっている。
  **生 grep はツールが読んだファイルの中身まで数える。** 行の種別で絞る

### 効果を主張するなら、同じ課題で両方を測る

片方だけ測って「改善した」とは言えない。新旧それぞれ 6 回以上流して比べる。

**差が出なかったときは「効果が無い」ではなく「この課題では再現しない」。**
実使用で 3/14 の失敗が、雛形では 6/6 になることがある。雛形が軽すぎる。

## 常時読みの量を数える

**常時読みが増えると、そこに書いていない指示まで守られなくなる。** 競合ではなく希釈。

面ごとに「常時」と「条件付き」を分けて数える。同じ総量でも効き方が違う。

```bash
cat ~/.kiro/steering/*.md | wc -m          # 常時
cat ~/.claude/skills/*/SKILL.md | wc -m    # 条件付き（description 一致で発火）
```

数えたら**上限を機械で見る**。上限は測った崖ではなく**増やさないための歯止め**で、
いまの構成に言い回しの直し程度の余地を足した値にする。スキルを1本足したら落ちるのが正しい。
上げるときは「何を落としたか」か「上げてよい実測」を添える。

→ 面ごとの配り分けは [README](../README.md#kiro-は常時と頼んだときだけを分ける)

## 踏んだ罠

いずれも**測定の失敗が、陰性の結果と同じ顔で出た**。結論が逆に出る。

| 罠 | 何が起きたか | 避け方 |
|---|---|---|
| 出力の語数で到達を測る | 「読まれていない」と誤判定し、撤退を決めた | 合言葉 + 対照 |
| 生 grep で発言を数える | ツールが読んだファイルの中身が混じり「宣言 4 件」。実際は 0 件 | 行の種別で絞る |
| 絞りすぎて投稿物を落とす | 発言だけ見て、`gh api` の payload にあるレビュー本文を落とした | `text` + `toolUse` |
| regex の錨が出力に合っていない | 行頭を要求して、箇条書きの接頭辞に当たらず 15/15 を 3/14 と読んだ | **出ているはずの回で1件当てる** |
| 分母を手で括る | レビューが実装に混ざる。全セッションを分母にする | 道具の記録から出す |
| 上限を本文だけで数える | 実ファイルより 180 字甘い判定になっていた | 実際に置かれる中身で数える |
| テストが検査対象から期待を読む | 設定を変えると期待も変わり、変異が緑のまま通る | **テスト側が期待を手で持つ** |

最後の2つは**自分の検査の中にある偽の緑**。`or not ...is_dir()` のような
**常に真になる条件**を書いていないか、指摘される前に自分で探す。

変異を当てて赤になるか確かめるときは、**件数ではなく落ちた項目の集合**を見る。
件数が同じでも中身が違うことがあるし、アンカーが外れて変異が当たっていないこともある。

## この測定自体の限界

- **到達は遵守を示さない。** 届いていて、知っていて、やらないことがある
- **遵守の測定は課題に依存する。** 軽い雛形では差が出ない
- **n は小さい。** 1条件 6 回では、4/6 と 6/6 の差は偶然で説明できる。
  方向が複数の判別子で一致しているかを見る
